## 何のサービスか

ダンススタジオ向けのスクール運営管理 SaaS。運営は合同会社セキレイ。
サービス名・ドメインは未定（仮称 Studio Flow）。

中核価値は「現金回収でも月謝管理がきちんと回る」こと。カード決済や口座振替は
初期スコープ外で、「誰から今月いくら受け取ったか／いないか」を帳面より速く分かる
状態にするのが第一。

利用者は4種類。

| ロール | 画面 | 端末 |
| --- | --- | --- |
| オーナー・スタッフ | `/admin/*` | PC |
| 講師 | `/staff/*` | スマホ（出欠を現場で付ける） |
| 保護者 | `/my/*` | スマホ |
| 入会・体験の申込者（未ログイン） | `/apply/<slug>` | スマホ |

## 技術構成

- Next.js 16（App Router、Server Components とサーバーアクション中心）
  + React 19 + TypeScript + Tailwind CSS v4
- Supabase（PostgreSQL / RLS / Edge Functions / pg_cron）、東京リージョン
- 認証はメール確認コード方式（パスワード無し）
- メールは Resend。Edge Function から送り、結果を `deliveries` に残す
- Vercel に main への push で自動デプロイ

## 設計の決めごと（守っているつもりのもの）

1. 全業務テーブルに `organization_id` を持ち、全テーブルで RLS 有効
2. アプリ層でも必ず `organization_id` で絞る。RLS は保険であって一次防御ではない
3. ロールはサーバーセッションから決める。クライアントで切り替えない
4. 日時は `timestamptz` で UTC 保存、表示は Asia/Tokyo。日付だけの列は `date`
5. 金額は税込・整数（円）。税率を併せて保存。浮動小数点は使わない
6. 物理削除をしない。状態変更で表す（唯一の例外は実績の無い校舎の削除）
7. 複数テーブルにまたがる書き込みは DB 関数（security definer）にまとめ、
   関数内で呼び出し元のロールを検査する

詳細は `docs/studio-flow-design.md`（設計書）。本文の冒頭の `CLAUDE.md` に
絶対条件がまとまっている。

## 見てほしいこと

優先順。

1. **テナント分離の抜け。** RLS ポリシー、security definer の関数、サーバー
   アクションで、他の `organization_id` のデータに到達できる経路が無いか。
   特に `supabase/migrations/*.sql` の関数と、`src/app/**/actions.ts`
2. **認可の抜け。** 講師（`/staff`）が売上・報酬・未納を見られないか。保護者
   （`/my`）が他の世帯の生徒に触れないか。URL や API を直接叩いた場合も含めて
3. **金額計算。** 月次請求の生成（`generate_invoices`）、兄弟割、イベント参加費の
   合算、入金と請求状態の同期。整数の扱い、重複請求の防止
4. **日付の境界。** JST の「今日」を使うべき箇所で UTC を使っていないか
5. **レッスンの再生成。** 出欠・欠席連絡・振替が付いた回を消さないルールが
   守られているか（`generate_lessons`）
6. **設計上の無理。** 今の構造で、後から足すときに壊れそうなところ
7. コードの読みやすさ・重複・命名

## 見なくてよいこと

- 見た目の好み（配色やレイアウト）。別途調整中
- サービス名・ドメインに依存する箇所（未定のため仮置き）
- スコープ外の機能（カード決済、LINE、講師報酬の自動計算、分析）。
  設計書 9.1 に「やらないこと」として明記している
